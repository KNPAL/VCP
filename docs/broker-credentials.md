# Encrypted broker sessions

KAN-28 now has an internal encrypted session store. AES-256-GCM uses a fresh 96-bit nonce and a 256-bit key obtained through an injected key resolver. The authenticated metadata binds the ciphertext to its secret-reference UUID, account hash, session revision, key ID and expiry. Key material is not stored in PostgreSQL. Decryption rejects altered metadata, ciphertext, wrong keys, malformed secret fields and expired sessions with the sanitized BROKER_UNAVAILABLE code.

`installBrokerSession` accepts independently verified authentication/static-IP proof from the trusted authentication boundary. It stores only an encrypted envelope and returns reference metadata. Encryption persistence, immutable session evidence and circuit restoration commit together. Failed persistence rolls back the new session. A fresh verified session revision is required to clear an authentication circuit; replaying an old revision cannot restore it.

`resolveBrokerSession` is internal worker code, not a UI/API endpoint. It joins the reference to the active, non-expired circuit revision and checks stored metadata before decrypting. Open circuits and superseded references fail closed. `referencedBrokerBackfillGateway` resolves immediately before each window, then delegates to the existing quota-limited gateway, which checks the circuit again before requests. Tokens are never put into queue payloads, result summaries or error messages. Plaintext exists transiently in process memory for request headers; JavaScript strings cannot be reliably zeroed. Temporary byte buffers are cleared where possible.

Synthetic verification covers randomized ciphertext, exact round trips, wrong keys, tampering, expired sessions, invalid headers, immutable storage, atomic rollback, circuit rejection, replay rejection and fresh-session restoration. Migration 18 creates the encrypted store. No actual broker credentials have been provisioned or real authentication performed.

The concrete authentication adapter calls only loginByPassword and getProfile. It verifies the returned account identity, uses separate global quota reservations, refuses redirects, bounds response size and elapsed time, and rejects HTML/null/403/error responses. Token claims only restrict expiry; successful provider profile verification establishes authentication. Expiry is capped at the earliest of the token expiry, exchange midnight and static-IP proof expiry. A failed attempt opens the prior session circuit without affecting a concurrently restored newer session. PIN, TOTP and refresh tokens are not persisted. This follows the official [SmartAPI User API](https://smartapi.angelone.in/docs).

Production configuration: mount a restricted, operator-managed secret directory and set BROKER_KEY_DIRECTORY. Each key is a canonical base64-encoded 32-byte value in `<keyId>.key`; keys are provisioned externally and are never generated silently. Set DATABASE_URL and REDIS_HOST/REDIS_PORT for the worker. An operator can run `node apps/worker/dist/provision-broker.js <protected-input-file>` with `login`, `ipProof` and `keyId` JSON fields. The input contains a one-use PIN/TOTP and must be protected and removed by the operator after use. The command emits reference/session/expiry metadata only; its error output is sanitized. Static-IP proof must come from independently verified deployment/account configuration, never a UI assertion.

KAN-28 is verified with synthetic broker responses, real local PostgreSQL/Redis and key-file fixtures. Live account access still requires actual operator-provided credentials, registered-IP verification and secret keys. Those deployment inputs have not been supplied or fabricated.
