# Historical backfill and checkpoints

KAN-32 persists immutable sync-run requests, resumable windows and immutable per-attempt evidence. Each request pins its listing, provider, daily interval, range, knowledge time, explicit verified calendar and expected sessions. Reusing a run ID with different evidence fails. Windows retain attempts, lease/fence token, next retry time, exact response report, parent range and typed failure reason.

Only one window per run can hold an unexpired lease. Expired attempts are retained as LEASE_EXPIRED; a new token fences the prior worker. Candle ingestion, revisions, change outbox, coverage and the window checkpoint commit in one serializable transaction. A stale token or expired lease rolls back the candle writes too. Migration 17 separates quota deferrals from failures: shared-budget waits retain immutable DEFERRED evidence and their retry delay without exhausting the window. The attempts field counts all reservations. Four failed or expired attempts exhaust the window; credentials/provider errors never cause endless retries. A retry after a process crash uses the existing run and subtracts committed coverage when preparing a new run, without rewriting old evidence.

KAN-33 has a tested planner and worker service. It requests a five-year horizon, reports whether 450 completed sessions are available, subtracts stored sessions and splits requests into at most 400 calendar days. Incomplete responses halve the affected ranges down to seven days; odd lengths may overlap to preserve every date while respecting that floor. Repeated bars are harmless because ingestion compares content hashes. Gaps at the floor remain PROVIDER_GAP; no EMPTY_OR_SUSPENDED classification is invented. Unknown calendars queue no requests. The concrete gateway checks mapped identity and expected sessions before requesting data, normalizes exact broker tuples, and rejects malformed or contradictory rows before checkpointing. Valid partial responses enter the subdivision path.

Migration 19 adds an immutable run binding to a credential reference, instrument snapshot and licensed source snapshot. The source must identify DAILY_CANDLES, ANGEL_ONE and the fixed historical endpoint, with current DOWNLOAD and STORE permissions. The worker revalidates this evidence before every window and resolves the current encrypted session immediately before fetching. Its registered backfill handler accepts only a run UUID. SQL due windows drive the five-second dispatcher, so lost Redis jobs can be rebuilt; deterministic identifiers and SQL leases/checkpoints prevent duplicate candle revisions. Exhausted failed jobs are not endlessly reset.

Trusted submission uses `node apps/worker/dist/submit-backfill.js <input-file>`. The JSON contains `preparation` (the prepareBackfill input, including a verified calendar) and `binding` (credentialReference, instrumentSnapshotId, sourceSnapshotId, exchange and symbolToken). The command prepares/resumes the run and pins the binding. No broker secrets enter that file or the queue. Actual licensed sources, mappings, official calendars and authenticated credentials must be provisioned before live use. Synthetic verification includes deleted Redis-job recovery, strict payload rejection, repeated submission, immutable binding and expired-source rejection.

KAN-39 exposes authenticated GET /api/v1/system/jobs with runId, UUID after cursor and bounded limit; GET /system/coverage/:listingId?provider=...; and equivalent listingId/provider filters on /system/data-gaps. The existing unfiltered data-gaps scan response is preserved. Responses show window state, attempts, retry state, exact returned/missing sessions, latest final candle/revision, last successfully committed window and rejected candle evidence. No lease tokens or credentials are exposed.

Coverage holes are recomputed against stored bars and the verified calendar through the full requested horizon, rather than only the last returned window. An unknown listing/provider/calendar remains UNKNOWN; null is not zero coverage. Per-window success does not imply full-run completion or the 450-session warmup requirement. All monetary/candle evidence retains the existing decimal-string contracts.

Verification uses synthetic data in vcp_test: same-ID retries/conflicts, concurrent claims, partial split/repair, empty floor responses, expired lease recovery, stale-write rollback, retry exhaustion, source isolation, authenticated pagination and invalid-query checks. No real broker downloads or financial fixtures are inserted into the application database.
